# Finishing a Development Branch

Confirm the final change has completed the project's independent quality-check and required checks. Evidence must describe the current tree: rerun affected verification after material edits or integration changes, and report unresolved failures. Do not add another whole-branch review or repeat an unchanged successful test suite merely to follow this skill.

Determine the repository, branch, base, worktree ownership, and uncommitted changes with read-only Git commands. Verify the intended target from the plan, upstream, or conversation before integrating.

Follow the integration action already authorized by the user. The design approval already covers commits, feature-branch pushes, creating the PR and the merge. First, if the project's rules require the user's approval for the merge, or the merge automatically releases, publishes or deploys to production - an environment that customers or users rely on (exception X2; an automatic deploy to an environment for checking behavior, such as staging, is not X2) - finish the reviewable result and put that question in the final message. Otherwise look at the deviations from the design - both the spec / plan record and the PR body's deviation section. If there are none, merge with the project's merge procedure once quality-check is complete. If there are any, they change what was approved: finish everything else but create the quality-check flag only after the user's confirmation, ask in the final message as a separate decision ("merge with these deviations?"), and merge after the user's confirmation. A deviation that appears after that confirmation needs a new confirmation. Do not present an approval menu again. End with the final message of `documents/development/development-policy.md` §1.0 "承認後の進め方".

For a project that promotes main to a production branch (`release` or similar), the X2 question covers everything that goes out (§1.0 "承認後の進め方" 8). Before asking, run `git fetch origin` and fix the end SHA of the source. List the PRs not yet promoted up to that SHA: with merge-commit promotion, `git log --first-parent --oneline origin/<release>..<SHA>`; with squash promotion, main's commits never become ancestors of the production branch, so start from the previous source (the SHA recorded in the last promotion PR, or the first-parent main commit whose tree equals `origin/<release>^{tree}`). Show the list and the short SHA in the final message. Promote exactly that SHA; anything that lands before or after the OK stays out. When this PR is not merged yet, add "this PR (after merge)" to the list; after the merge, if the first-parent range `<the SHA you asked with>..<this PR's merge commit>` holds only this PR, use that merge commit as the end, otherwise rebuild the list and ask again. After the OK, the AI merges and promotes; do not hand those operations back. The commands depend on the merge method: the project's own procedure holds the exact steps.

A project with no remote integrates into main without a PR, with main open in another worktree: (1) finish quality-check in the feature worktree so the flag matches HEAD; (2) before touching the main checkout, check that `git push . HEAD:main` is usable in this project (no deny rule in the agent settings such as `Bash(git push:*)`, no project rule against it); (3) if it is, in the checkout that has main open, run `git switch --detach`; in the feature worktree, run `git push . HEAD:main` (git refuses anything but a fast-forward); in the main checkout, run `git switch main`; (4) if it is not, use the local merge of the `branch-workflow` skill, run where the flag is (the gate reads the flag of the checkout that runs the command, and the main checkout has none): in the main checkout, `git switch --detach`; in the feature worktree, `git switch main`, `git merge --no-ff <feature>`, `git switch <feature>`; in the main checkout, `git switch main`; (5) delete `.quality-check-passed`. If the push or the merge is refused after the main checkout was detached, put both checkouts back (`git switch <feature>` in the feature worktree if it is on main, then `git switch main` in the main checkout) before stopping. Use this only when no remote exists. With the feature and main in one checkout, finish quality-check on the feature, switch to main and run `git merge <feature>`: the quality gate checks that the flag names that branch's tip and that main has nothing the branch lacks. Delete `.quality-check-passed` after any merge into main.

Keep the project's branch protections and quality gate. A local merge or main push is not a substitute for a required PR. Investigate rejected pushes; do not force-push or bypass a gate without explicit applicable authorization.

When creating a PR, describe the problem, resulting behavior, and observed checks. Preserve the worktree for feedback. On an environment-owned worktree, use supported platform operations and leave cleanup to its owner.

Clean up only a worktree you created and only after its work is safely integrated or explicitly discarded. Check for uncommitted and ignored files before removal. Never force removal of files that exist nowhere else; resolve their disposition with the user. Do not infer permission to discard work from an integration request.
