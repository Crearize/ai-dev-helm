# 静的チェック基準カタログ

技術非依存の「**何を機械的にチェックすべきか**」の標準。AI が主体で開発を行うプロジェクトにおいて、決定的チェック（Lint / 静的解析）で担保すべき項目を A1〜F2 の25カテゴリに整理する。

**設計原則: 機械判定できるものは AI レビューに委ねず、決定的チェックにする。**

AI レビュー（ペルソナレビュー）は確率的であり、同じコードに対して毎回同じ指摘が出るとは限らない。`any` 禁止・ワイルドカード import 禁止・空 catch のような**機械判定できるルールを AI レビューで担保すると、チェック漏れが構造的に起こりうる**。本カタログはその境界を引くための基準であり、ここに載る項目は原則として Lint 側に寄せる。

分類は業界標準のタクソノミ（Sonar 品質モデル: Bug / Vulnerability / Security Hotspot / Code Smell、Semgrep レジストリ: security / correctness / best-practice / maintainability / performance / portability）と、AI 生成コードの欠陥研究（ハルシネーション import、廃止 API 使用、エラー握りつぶし、ハードコード秘密情報等）を突き合わせて策定した。

本カタログは技術非依存の**基準**であり、実行機構ではない。プロダクトへの実際の配線（どのツールでどのルールを有効にするか）は `lint-scaffolding` スキル（フェーズ3で提供）が本カタログを判断基準として行う。

## 1. カタログの読み方

各カテゴリ表は次の4列を持つ。

| 列 | 意味 |
|---|---|
| # / カテゴリ | カテゴリ番号と名称。**🤖 は AI 生成コードで特に頻発するカテゴリ**を示す（後述） |
| チェック内容の例 | そのカテゴリで機械的に検出したい違反の代表例。網羅リストではない |
| 一般的な実現手段 | 代表的なツール・ルール。プロダクトのスタックに応じて読み替える |
| 採用基準 | どのようなプロダクトで必須 / 推奨 / 任意か（下記） |

**「チェック内容の例」は代表例であり、そのカテゴリで担保すべきルールを尽くしていない。** カタログの例に載っていない Lint 担保可能なルールは、プロダクト側で Lint 設定・追加規約として定義してよい（その際は該当するカテゴリ番号を付記し、どのカテゴリの具体化かを辿れるようにする）。

### 🤖 マークの意味

🤖 が付いたカテゴリは、**AI 生成コードで頻発する欠陥領域**である。人間が書いたコードでも起こるが、AI による生成では発生率が有意に高く、かつレビューで見落とされやすい。**`lint-scaffolding` は 🤖 カテゴリを優先導入対象とする** — 導入コストの制約でカテゴリを絞る場合、同じ採用基準の中では 🤖 から先に配線する（採用基準との優先順位は後述）。

対象カテゴリ: A2（非同期・Promise の正しさ）、A3（エラーハンドリング規律）、B1（シークレット・機密）、B2（コードレベル脆弱性パターン）、B3（依存の健全性）、C3（デッドコード）、C6（マジックナンバー・ハードコード値）、E1（テスト妥当性）。

### 採用基準の定義

| 採用基準 | 意味 |
|---|---|
| **必須（全プロダクト）** | 言語・スタックを問わず全プロダクトで担保する。採用しない場合は理由を記録する |
| **推奨（該当技術があるプロダクト）** | 該当する技術要素（非同期処理、DB アクセス、複数モジュール構成、フロントエンド等）を持つプロダクトでは担保する。該当技術がなければ対象外 |
| **任意（プロダクト判断）** | プロダクトの性質・規模に応じて採否を判断する |

採用基準は `lint-scaffolding` がカバレッジマップを作成する際の判断基準である（詳細は §3）。

**採用基準と 🤖 の優先順位**: 導入コストの制約でカテゴリを絞る場合も、**必須カテゴリを先に満たす**。🤖 は必須カテゴリ内・同一採用基準内での配線順序付けに使うものであり、**🤖 が採用基準を飛び越えることはない**（🤖 の付いた推奨カテゴリが、🤖 の付かない必須カテゴリに優先することはない）。

## 3. 補足

- **N+1 検出は二段構え。** N+1 の静的検出は本質的にヒューリスティック（「ループ内のクエリ / lazy load 呼び出し」パターン）であるため、D1 では「静的検出（ast-grep、スタック別ルール）+ 実行時検出（開発 / E2E 環境でのクエリカウント）」の二段構えを標準とする。静的検出のみで担保済みとみなさない。
- **採用基準はカバレッジマップの判断基準。** 各カテゴリの採用基準は、`lint-scaffolding` がプロダクトのカバレッジマップ（どのカテゴリをどの手段で担保するかの台帳）を作成する際の判断基準として使う。カテゴリを採用しない場合も、その事実をカバレッジマップに記録して「チェック自体が消える」ことを防ぐ。
- **Semgrep は代替エンジン。** 汎用 AST エンジンの既定は ast-grep（`@ast-grep/cli`）とする。Semgrep は同等の役割を担える代替エンジンとして記載するに留め、既定にはしない（Python 製で Windows ネイティブ対応が弱いため）。

## 4. 規約文書との関係

**Lint で担保可能な項目の記載先は本カタログである。** 規約文書（`shared/documents/coding-rules/`、`stacks/<stack>/documents/coding-rules/`、および `stacks/<stack>/rules/`）が扱うのは、**Lint で担保できない原則・文脈依存ルール**とする。

| 対象 | 記載先 |
|---|---|
| 技術非依存かつ Lint（本カタログ A1〜F2 + 事前ビルド Lint 資産）で完全に担保される項目 | 本カタログに集約する。規約文書の本文には記載しない |
| **言語・FW 固有かつ Lint 担保可能な項目**（例: forwardRef 禁止（React）、try-with-resources（Java）） | `stacks/<stack>/rules/` に残置し、対応するカタログ番号を付記する。**本カタログは技術非依存の基準のみを持ち、固有ルールの本体は持たない** |
| Lint で担保できない原則・文脈依存ルール（設計判断・命名の妥当性・ドメイン固有の制約など） | 規約文書に記載する |

規約文書と Lint の二重管理を避けるための原則である。規約文書に残る項目には、対応するカタログカテゴリ番号（A1〜F2、該当がある場合）を付記する。

**プロダクトが当該 Lint を採用しない場合**、`lint-scaffolding` のカバレッジマップで該当カテゴリを「AI レビュー担保」に割り当て、レビューガイド（プロダクトでは `.github/review-*.md`）側に観点として残す。カテゴリを採用しないことでチェック自体が消えることはない。

### 4.1 移行注記（フェーズ3までの扱い）

**ハーネスが提供する Lint 資産（`shared/lint/` の汎用資産、`stacks/<stack>/lint/` のスタック別資産、`lint:all` の配線）はフェーズ3まで存在しない。** ただし決定的チェックそのものが存在しないわけではない — **プロダクト側の既存静的チェック（ESLint / Checkstyle / tsc 等、CLAUDE.md に登録された静的チェックコマンド）で担保済みの項目は、そのまま Lint 担保として扱う**。それ以外の項目を AI レビュー（ペルソナ + レビューガイド）で担保する。したがって:

- レビューガイドからのカタログ項目の除外は、対応する Lint が（ハーネスの Lint 資産・プロダクト既存設定のいずれであれ）実際にプロダクトへ配線されていることを確認した後に行う
- **フェーズ3までは、Lint 担保予定の項目を規約文書から削除せず、`> Catalog: <番号>` 参照を付けた移行形で残す。** 完全削除は対応する Lint 資産が配線された後に行う
- 「Lint 担保済み項目は規約文書に記載しない」最終形は本カタログの新設時点から方針として適用するが、その項目のチェックが失われないよう、移行期間中は上記の移行形と AI レビュー側の観点で担保を維持する
- **スタック別ルール文書（`stacks/<stack>/rules/`）の項目は Lint 配線後も削除せず、「項目名 + カタログ番号 + Lint 資産参照」の形式に縮約する（削除は汎用規約文書側のみ）。** これらの項目は §4 のとおり本カタログへ移さないため、削除するとルールの本体が失われる

### 4.2 汎用化の昇格ルール

特定言語の文書に由来するルールでも、**概念が複数言語に共通するものは汎用ルールへ昇格**し、言語別の具体例を添えて記載する。プロダクト側は自分の言語に応じて具体ルール（Lint 設定や追加規約）を足せばよい。

**昇格の判定基準: 「2つ以上の主要言語で同じ概念のルールが成立するか」。**

**昇格の判定と記載先の判定は独立した2段階である。**

1. **第1段階（昇格判定）**: 上記の基準で「汎用概念か / 特定言語固有か」を分類する
2. **第2段階（記載先判定）**: §4 の Lint 担保済み原則で「本カタログに載せるか、規約文書に載せるか」を決める

第1段階で汎用と判定されても、Lint で担保可能であれば最終的な記載先は本カタログ側になる。

**昇格例**（いずれも Lint 担保可能なため、記載先は本カタログ）:

| 昇格したルール | 言語別例 | カタログ上の記載先 |
|---|---|---|
| ワイルドカード import 禁止 | Java `import java.util.*` / Python `from x import *` | A1 |
| フルパッケージ名修飾の禁止 | Java の完全修飾名直書き `java.util.List` / C# の `System.Collections.Generic.List<T>` | A1 |
| 未使用 import 禁止 | TypeScript / Java / Python 共通 | C3 |
| マジックナンバー禁止 | TypeScript / Java / Python 共通 | C6 |

## 5. 配布時の注記

本カタログは基準の定義であり、ハーネスが提供する実行機構（`shared/lint/` の汎用 Lint 資産、`stacks/<stack>/lint/` のスタック別資産、`lint-scaffolding` スキル）はフェーズ3で提供される。それまでの担保方法は §4.1 を参照。

**本文中のパスはハーネスリポジトリ（ai-dev-helm）表記であり、配布先のプロダクトでは下表の対応で読み替える。**

| ハーネスリポジトリ | 配布後（プロダクト側） |
|---|---|
| `shared/documents/`（本カタログ・`quality-policy.md` 等） | `documents/development/` |
| `shared/documents/coding-rules/` | `documents/development/coding-rules/` |
| `stacks/<stack>/documents/coding-rules/`（スタック別の詳細規約） | `documents/development/coding-rules/` |
| `stacks/<stack>/rules/` | AI ツール別に `.claude/rules/` / `.cursor/rules/` / `.codex/rules/` |
| `shared/review-guides/` / `stacks/<stack>/review-guides/` | `.github/review-*.md` |
| `shared/lint/` / `stacks/<stack>/lint/` | フェーズ3の配布実装でプロダクト側パスを確定する（未定） |

> プロジェクトスキルを導入していない（superpowers スキルのみ導入した）プロダクトでは、本書が参照する `quality-check` / `lint-scaffolding` スキルのファイルが存在しない。これらの参照は該当ファイルを導入した時点で有効になる。
