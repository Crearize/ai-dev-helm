# AI Quality Policy

AI が主体で開発を行うプロジェクトのための品質ポリシー。AI Coding Policy（どう書くか）に対して、本ドキュメントは **AI Quality Policy（何をもって「品質を確認した」と言えるか）** を定義する。

前提となる問題認識は2つある。

1. **テストの Green は「正しさ」を保証しない。** テストが通ることは「書いたテストの範囲で期待どおりに動いた」ことしか意味しない。期待値そのものが誤っていれば、Green は誤りを追認するだけになる。
2. **実装と検証が同じ最適化ループの中にある。** 実装した AI 自身がテストを書くと、テストを通すことが目的化し（リワードハッキング）、実装の誤りをテストが一緒に間違えるという相関故障が起きる。

このポリシーは、リスクに応じたゲートの強度・テスト層の選び方・期待値の根拠（テストオラクル）・反復工程の打ち切り基準を定めることでこの2点に対処する。`quality-check` スキル（`skills/project/quality-check/SKILL.md`）は本ポリシーを参照して実行され、リスクレベル判定・ゲート適用・ループ防護の判断根拠を本ドキュメントに置く（本ドキュメントは方針の定義、スキル側は実行手順であり、数値・基準はスキルに複製せず本書を単一ソースとする）。追加テスト（ミューテーション・E2E）の提案と実行は `test-recommendation` スキル（`skills/project/test-recommendation/SKILL.md`）が担い、その実行規律は本書 §2 を参照する。

> 参考記事: [AIが書いたテストのGreenは何を保証しているのか](https://qiita.com/y0us91/items/2feffd2cc6c672717973)（Qiita, y0us91）

## 1. リスクレベル定義

変更差分から `quality-check` Step 1 でリスクレベルを判定し、`.quality-check-report.json` に `risk_level` として記録する。

| レベル | 判定基準（変更内容ベース） |
|---|---|
| High | 認証・認可、決済・課金、データ整合性に関わる書き込み処理、外部 API 連携、マイグレーション、セキュリティ設定 |
| Medium | 上記以外の業務ロジック（Service 層 / ドメインロジック / 状態遷移を持つ処理） |
| Low | UI 表示・文言・スタイル、ドキュメント、設定値の軽微な変更、純粋なリファクタ |

複数領域にまたがる場合は最も高いレベルを採用する。判定に迷う場合は1段階高いレベルに倒す。

High の判定は、該当領域の**実装コード**に直接差分がある場合に適用する。テストコードのみ・型定義のみ・ログ出力のみの変更は、その領域に属していても High の根拠にはしない（Medium 以下として判定する）。

## 2. リスクレベル別ゲートマトリクス

| ゲート | High | Medium | Low |
|---|---|---|---|
| 静的チェック（決定的チェック層） | 必須 | 必須 | 必須 |
| ユニットテスト | 必須 | 必須 | 必須 |
| test-design スキル（テストオラクル定義） | 必須 | 必須 | 不要 |
| ミューテーションテスト（差分スコープ） | 提案ベース（quality-check Step 5 / test-recommendation スキル。ユーザー判断で実行・非ブロック） | 同左 | 同左 |
| ペルソナレビュー | 変更内容で決まる（quality-check Step 4 の適用判定表） | 変更内容で決まる（同左） | 変更内容で決まる（同左） |
| E2E | 提案ベース（quality-check Step 5 / test-recommendation スキル。ユーザー判断で実行・非ブロック） | 同左 | 同左 |

追加テスト（ミューテーション・E2E）の提案ヒューリスティクス（推奨度と条件）・提示・実行手順は `test-recommendation` スキルを正とし、本書には転記しない。提案の見送り・実施後の生存ミュータントは**記録のみ・非ブロック**である（E2E を実施して失敗した場合のみ、実バグとして修正必須）。

実行時間バジェットはプロダクト側のハーネス設定ファイル（下記「上書きの契約」）で上書き可能とする。

> **上書きの契約**: 上書きはプロダクト側のハーネス設定ファイル（`CLAUDE.md` / `AGENTS.md` / `.cursorrules` のうちプロダクトが使用するもの。複数を併用する場合は全ファイルに同じ値を記載する。値が食い違う場合は最も厳しい値を採用し、食い違いの事実をユーザーにエスカレーションして是正を求める）に次の記法で記載する。
>
> ```markdown
> ### Quality Gate Overrides
> <!-- quality-policy.md §2 の契約に従う -->
> - mutation_budget_minutes: 15
> ```
>
> 上書きキーは `mutation_budget_minutes` の1つのみとする（上の例の値は本書の既定値そのもの）。ブロックを置かない場合、および記載のないキーは、本書の既定値が適用される。加えて、上書きの解釈と運用は次に従う。
>
> - ゲートパラメータ（実行時間バジェット）を変更するハーネス設定ファイルの差分は「ハーネスのみ変更の免除」の対象外とし、必ず quality-check（適用判定表に従うレビュー）を通す（hook の免除判定にも同カーブアウトが実装されており、ゲートパラメータ変更を含む差分はフラグなしでのマージがブロックされる）。ゲート制御面ファイル（quality-check スキル・スキーマ・`skills/project/test-recommendation/**`（Step 5 は完了条件の構成要素であり、判定・提示・実行・記録の規定は同スキルを単一ソースとするため）・レビューガイド・hook 実体（`init` がリンクとして作成する `.claude/skills` リンクノードと `.claude/hooks` ツリーおよびそれらの `.codex/**`・`.cursor/**` コピーを含む）・hook 登録ファイル・`.codex/config.toml`（ファイル全体 — inline `[hooks]` テーブル・`[features]` の hook 無効化・`[[rules]]` の deny 判定を持ち得る）・MCP 登録ファイル（`.claude/mcp.json` / `.codex/mcp.json` / `.cursor/mcp.json`）・`.claude` / `.codex` / `.cursor` の `agents/` `commands/` `prompts/` `rules/` ディレクトリ・`.claude/settings.json` と `.claude/settings.local.json`（**ファイル全体**が制御面。hook はキー単位の解析をせず、`hooks` ブロック・`disableAllHooks` / `allowManagedHooksOnly` 無効化キー・`permissions.deny` ルールリストに限らず、`permissions.allow` のみの変更もブロックする） — パスは大文字小文字を区別せず判定する）の差分も同様に hook が免除対象外として扱い、`Gate control-plane changed:` でブロックする（対象パス集合は `quality-check` SKILL.md「ハーネスのみ変更の免除」を正とする）。
> - 既定値から乖離した上書きを適用した場合は、その事実と理由を `.quality-check-report.json` の `gate_parameter_overrides` に記録する（キー定義は `quality-check-report.schema.md` を参照）。
> - HTML コメント（`<!-- -->`）の内側、および markdown コードスパン・コードフェンス内に置かれた `### Quality Gate Overrides` ブロックとキー記載は**宣言とみなさない**（無効。既定値が適用される）。テンプレートはこの形（コメントアウト）で雛形を配布する。有効化はコメント解除によって行い、その編集自体がマージゲートの対象になる。quality-check 実行体も hook もこの解釈に従う。
> - キーの照合は**大文字小文字を区別せず、区切り文字（`_` / `-` / 空白）も区別しない**（`Mutation-Budget-Minutes` は `mutation_budget_minutes` と同一の宣言とみなす）。正規表記は snake_case とし、それ以外の表記を見つけた場合は宣言として扱ったうえで、正規表記への是正をユーザーに求める。quality-check 実行体も hook もこの規則に従う。
> - **1つのファイル内に同一キーを複数回記載してはならない（MUST NOT）。** 複数記載があり値が食い違う場合、値は不定として扱う: quality-check 実行体はユーザーにエスカレーションして是正を求め、hook は宣言状態を判定不能（免除なし）として扱う。
> - hook の免除判定はこの規則とは別軸で、ハーネス設定ファイルの差分に `Quality Gate Overrides` / `mutation_budget_minutes` の文字列変更が含まれれば有効性を解析せず免除しない（過検出でよい）。

**マトリクス優先順位原則（一方向）**: 本マトリクスは各ゲートの**強度**（要否の厳しさ）を定める。`quality-check` の変更領域別ステップ適用テーブルがステップを実行しないと定めている場合、リスクマトリクスの「必須」はそれを覆さない（逆方向の上書きはしない）。領域テーブルで `-` のステップはリスクレベルに関わらず実行しない。test-design の照合は領域テーブルの Step 3 欄に従う（ユニットテストを実行しない領域では実行せず、`out_of_scope` として記録する。記録キーは `.quality-check-report.json` の `test_design`）。**未実行理由の記録もこの優先順位に従う**: 領域による対象外（`out_of_scope`）と Low リスクによる非実行（`not_required`）の双方に該当する場合は、領域による対象外を先に記録する。ミューテーション・E2E の未実行理由（`not_configured` / `empty_scope` / `scope_error` 等）の記録は `test-recommendation` スキルの未実行理由の優先順位表に従う。静的チェック（決定的チェック層）行が担保すべき内容はチェック基準カタログ（`static-check-standard.md`、配布後は `documents/development/static-check-standard.md`）に定義する。

なお、マトリクス自身がリスクベースで「不要」と定めている場合（Low の test-design）はそのとおり実行しない。本原則は領域テーブルが実行しないと定めたステップをリスクレベルで復活させないためのものであり、その逆ではない。

**適用例**: ペルソナの起動は変更内容で決まる（`quality-check` SKILL.md Step 4 の適用判定表）。E2E の提案要否もリスクレベル単独では決まらない（docs / infra のみの変更は test-recommendation のヒューリスティクスで「提案しない」に該当する）。

**ミューテーションテストの提案についての注記**: 提案はミューテーションテストが導入済みのプロダクトでのみ行う。プロダクトにミューテーションテスト設定（Stryker / PIT）が存在しない場合は提案せず、`mutation: { executed: false, reason: "not_configured" }` を記録した上で、必要なら `lint-scaffolding` の実行を案内する（`test-recommendation` スキルと同内容）。

**ミューテーションテストの実行ポリシー**: ミューテーションテストは**ローカルで実行し、CI には組み込まない**（実行時間がそのままコストになるため）。CI はビルド確認の位置づけを維持する。

**ミューテーションテストの実行時間バジェット**: 1回の実行あたり既定**15分**（上記「上書きの契約」の `mutation_budget_minutes` で上書き可）。差分スコープが変更行・変更クラスである限り通常は超過しない。超過時は、リスクレベルの高いファイル優先で対象を絞って**1回だけ**縮退再試行し、絞った事実を `mutation.scope_reduced` として記録する。それでも完走できない場合は正規 outcome として `aborted_reason: "unmeasurable_within_budget"` を記録して先へ進む（非ブロック）。縮退再試行・提示・再試行の実行手続きと実行回数の上限は `test-recommendation` スキルを正とする（本段落は値の定義 — 唯一の数値 15分 と縮退再試行1回・記録キー — のみを持つ）。ミュータント単位のタイムアウトは Stryker / PIT の組み込み機構をそのまま使う。

**差分スコープの定義**: 「差分スコープ」はツールが対応できる最小粒度とする — Stryker は**変更行**（事前ビルドの `lint/mutation/stryker.diff.config.mjs` が、ベース ref との merge-base に対する**作業ツリー**の差分（`git diff -U0 <merge-base>`）の hunk を行範囲として `mutate` に渡す。ツールはディスク上のファイルを変異させるため、未コミットの編集も含めて行番号を一致させる）、PIT は**変更クラス**（変更された production クラスを `targetClasses` に設定する。`mutationDiff -PmutationDiffBase=<base>`）。変更ファイル全体を対象にしない — 1行の変更でファイル全体を対象にすると、スコアは変更ではなくそのファイルの既存テストを測ってしまう（例外: glob 特殊文字を含むパス（Next.js の `[id]` 等）は Stryker の範囲指定が使えないため、そのファイルのみファイル単位に縮退する）。ベース ref は `quality-check` Step 1 の差分判定と同じ基幹とする（既定は `origin/main`、無ければ `origin/master` を探索。基幹が異なるプロダクトは `MUTATION_BASE_REF` / `-PmutationDiffBase` で Step 1 と同じ ref に揃える）。使用した ref を `mutation.base_ref` に記録する。`scope: "changed_files"` は旧配線の暫定値であり、計測結果の解釈に使ってはならない（`lint-scaffolding` の再配線を促す）。

**空スコープと導出失敗の区別**: 変更が除外対象（テスト・型定義・生成物）のみ、または変更行・変更クラスにミュータント点がない（実行後にミュータント数 0 と判明した場合を含む）ときは**空スコープ**であり、`mutation: { executed: false, reason: "empty_scope" }` を記録する。空スコープの正規のシグナルは、差分実行の**終了コード 0 + 明示メッセージ**、または実行結果のミュータント数 0 である。ベース ref が解決できない等で差分実行が**非 0 終了**した場合は**導出失敗**（`reason: "scope_error"`）であり、`empty_scope` として記録してはならない — 解消（ベース ref の fetch、`MUTATION_BASE_REF` の設定）を試み、解消できなければ非ブロックで記録してユーザーに提示する（手順は `test-recommendation` スキルを正とする）。本段落は値の定義（`empty_scope` / `scope_error` の区別と正規シグナル）を定め、縮退・提示・再試行の実行手続きは `test-recommendation` スキルを正とする。

**トリアージ**: ミューテーションを実施した場合、生存した各ミュータントに次のいずれかの決定を付ける。通過判定はない — スコアと生存台帳は参考情報として提示し、対処範囲（その場でテスト追加 / 台帳に持ち越し / 対処不要と判断）は `test-recommendation` スキルの規定に従いユーザーと合意する（いずれを選んでもフラグ作成をブロックしない）。

| 決定 | 意味 |
|---|---|
| `killed` | テスト追加により検出できるようになった変異（red-green 検証を経て主張する） |
| `equivalent` | 動作が変わらない変異（等価ミュータント）。理由を1件ずつ記録する |
| `accepted` | 振る舞いに影響しないことが確認できる変異。カテゴリを `logging`（ログ・監視出力のみ）/ `defensive_guard`（契約上到達しない防御分岐）/ `type_only`（実行時挙動のない型・宣言）/ `ui_text`（表示文言）/ `dev_only`（開発時のみのコード）の**閉集合**から1つ選び、理由を記録する。「テストが困難」はカテゴリではない |
| `unresolved` | 振る舞いに影響するが、テストによる検出に至らなかった変異。理由を記録する。memo-linked の生存は対処提案の優先度を上げる |
| `untriaged` | 未判断（台帳に記録して持ち越し可・非ブロック） |
| `tool_false_negative` | ツール偽陰性（ツールの計測が信頼できない変異）。`score_raw` はツール算出の生値でありこれを含む。件数を台帳に明示し、スコアの解釈時に差し引いて読む |

本表は**値の閉集合と意味の定義**である。判定手続き（red-green 検証の手順・`equivalent` の判定基準の詳細・`tool_false_negative` の機械判定条件）は `test-recommendation` スキル「トリアージ規律」を正とする。

memo-linked とは、テスト設計メモ（§4）の「保証すべき状態遷移・不変条件」「ファルシフィケーション項目」に対応する変更行のミュータントを指す（記録キーは `mutation.survivors[].memo_linked`）。

**ツール status との対応**: killed・生存はツールのミュータント status で機械的に定める。killed = Stryker `Killed` + `Timeout` / PIT `KILLED` + `TIMED_OUT`。生存（`survivors` 台帳の対象）= Stryker `Survived` + **`NoCoverage`** / PIT `SURVIVED` + `NO_COVERAGE` — 変更行にテストが1本も到達していない `NoCoverage` は「検出できない変異」の最たるものであり、必ず生存として扱う。集計外（`mutants_total` にも分母にも含めない）= `Ignored`（除外種別）と `CompileError` / `RuntimeError` / `NON_VIABLE`。`score_raw` は**最後の実行時点**のツール算出値を記録する（再計測を含む。`mutation.runs` と整合）。

**ミュータント種別**: 事前ビルド設定は振る舞いに影響する種別だけを既定で有効にする（Stryker は非振る舞い系の種別を除外し `ignoreStatic` を有効化 — 正確な除外リストは配布設定 `lint/mutation/stryker.config.mjs` を単一ソースとし本書には転記しない。PIT は `DEFAULTS` グループ）。除外されたミュータントはスコアの分母に含まれない。プロダクトが種別を戻す場合は自プロダクトの設定側で行う（`lint/README.md`）。

**担保範囲の注記**: ミューテーションの実行結果は行網羅・配線検証の証明ではない（詳細は `test-recommendation` スキルの担保範囲注記を参照）。

**ペルソナレビュー行についての注記**: 適用ペルソナセットの具体的な条件（適用ペルソナは変更内容による適用判定表で決まる）は `quality-check` SKILL.md Step 1 の適用判定表を正とする（サイクルルールは同 Step 4。§5 参照）。

## 3. テスト層選択の原則（テストトロフィー）

**原則: テストの本数ではなく、Failure Mode に対して最も適切なテスト層を選ぶ。**

「テストトロフィー」とは、静的解析を土台に置き、その上のユニットテストと統合テストを厚く、頂点の E2E を最小限に保つテスト配分モデルである。本ハーネスでは土台の静的解析層を Step 2（決定的チェック層）が担う。

カバレッジ率やテスト件数は目的ではない。「この変更はどう壊れうるか（Failure Mode）」を先に列挙し、その壊れ方を最も確実に捉えられる層でテストする。

| Failure Mode | 推奨テスト層 | 例 |
|---|---|---|
| 入力境界（ゼロ・負値・null・オーバーフロー・精度） | ユニット | 金額計算の境界値 |
| 状態遷移・不変条件 | ユニット + 統合 | 注文ステータスの遷移制約 |
| 並行・リトライ・冪等性 | 統合（DB/キュー状態の観測込み） | 二重配信防止 |
| 外部依存（API・時刻・乱数） | 統合（契約テスト・スタブ境界） | 外部 API 失敗時の挙動 |
| 権限・認可 | 統合（+ E2E はシナリオ経路に含まれる場合） | 他ユーザーのリソースへのアクセス拒否 |

**統合テストの実行位置**: 統合テストは Step 3 のテストコマンドに含めて実行する（テストコマンドの定義はプロダクトの CLAUDE.md）。上表で「統合」を推奨層としたケースに独立したゲートは設けない。

**カバレッジ目標との関係**: カバレッジ目標（`development-policy.md` §9）は**下限**として維持する。本節が否定するのは、カバレッジ率の達成をテスト十分性の**証明**として扱うことである。なおミューテーションスコアはカバレッジ率とは別の指標である（カバレッジは「実行された行の割合」、ミューテーションスコアは「意図的な変異をテストが検出できた割合」を測る。数値の近さに意味はない）。

## 4. テストオラクル原則

**テストオラクル（Test Oracle）**: テストの実行結果が正しいかどうかを判断する基準・情報源（仕様書、要件、計算根拠など）。DB 製品の Oracle とは無関係。本ドキュメントでは「テストオラクル（期待値の根拠）」と表記する。

原則は次のとおり。

- **期待値の根拠は実装より先に定義する。** 各テストの期待値がどこから来たのか（仕様書・要件・計算根拠）を、実装コードを書く前に明示する。
- **実装の出力をそのまま期待値にすることを禁止する。** 実装を動かして得られた値をコピーして期待値に据える行為は、実装の誤りをテストが追認する構造そのものであり、検証として無効である（スナップショットの無検証な更新も同じ）。
- テストコードを書けることと、正しいテストオラクルを設計できることは別能力である。前者ができるからといって後者が担保されるわけではない。

High / Medium リスクの変更では、実装**前**に `test-design` スキルを実行してテスト設計メモを作成する。メモには最重要リスク・保証すべき状態遷移と不変条件・Failure Mode からテスト層へのマッピング・テストオラクル定義・ファルシフィケーション項目（「この実装が間違っていることを証明する」ための入力・シナリオ候補）を含める。`quality-check` Step 3 はこのメモとテストを照合し、メモが存在しない場合はエラーにせずその場で `test-design` を遡及実行して不足テストを補完してから先に進む。

## 5. 反復工程のループ防護

ペルソナレビューで過去に発生した「指摘 → 修正 → 再指摘」の無限ループと同じ問題は、Lint 修正でも起こりうる。

**原則**: 反復するのは quality-check の**外側サイクル**ただ一つである。各工程（Lint・テスト・ペルソナレビュー）は工程ごとの独立したループを持たず、サイクルの中で**1回ずつ実行**し、その結果を最後のペルソナレビューに入力として渡し、統合された指摘をサイクル末尾でまとめて対応する。工程単位のループを置かないのは、工程ごとに上限を持つと最悪ケースがその合算になるためである。機械的チェックが通ってからレビューする（前段の失敗が残ったサイクルではペルソナレビューを行わない）。実行時間バジェットは追加テスト（ミューテーション）の実行規律として §2 に定義し、Lint・ペルソナレビューにはバジェットを設けない。追加テスト（Step 5）も同じ規律に従い、ミューテーションの「テスト追加 → 再計測」の反復を持たない（再計測は対処をまとめて1回。実行回数の上限は `test-recommendation` スキル、バジェットは §2 を正とする）。

**サイクルの構成**: 1サイクル = Step 2（ビルド + 静的チェック）→ Step 3（テスト + テスト設計メモ照合）→ **Step 2〜3 の残存（解消できなかった違反・失敗テスト）があれば Step 4 を実行せずサイクル終了** → Step 4（ペルソナレビュー。適用判定表で選択）→ 統合指摘の対応。2サイクル目以降は、直前サイクルの統合指摘に**高または中**の指摘が残っていた場合にのみ実施する（それ以外は Step 5（追加テスト提案）へ進む）。

| 項目 | 規定 |
|---|---|
| サイクル上限 | **3サイクル** |
| 停滞検出 | 直前サイクルと**同一の高指摘**（同一箇所・同一内容）が再度残った場合は、上限を待たず打ち切る（同じ修正を繰り返しても収束しない兆候） |
| 構造的停滞 | 1 サイクルで同一クラスの高指摘（同一ファイル群ではなく、同一の機構・同一の設計判断に起因すると統合時に判定できる指摘）が **3 件以上** 出た場合。修正を続けず構造的問題として報告する |
| 上限到達・停滞時の挙動 | 高指摘を記録してユーザーに判断を仰ぐ。選択肢は ①残存指摘を受容して通す（`gate_override` に記録）②方針を変えて追加サイクル（上限は同数）を実施（変更する方針を明示させ、`cycle_extensions` に記録）③中断。②で方針の変更がない再実行は認めない。構造的停滞では選択肢は ①設計に戻す ②受容して通す（`gate_override`）③中断（方針変更による追加サイクルは選択肢に含めない） |

ペルソナレビューの適用ペルソナ（適用判定表）は `quality-check` SKILL.md **Step 1**を正とし、4-3 サイクルルールは同 **Step 4**を正とする。本ドキュメントからは参照のみとする（二重管理を避けるため、詳細の追記・改変は SKILL.md 側で行う）。ペルソナセットの選択が変更内容で決まる点は §2 のペルソナレビュー行注記を参照。

**検証レビュー（サイクル2以降）**: サイクル2以降の Step 4 は、前サイクルで高・中指摘を出したペルソナのみによる検証レビュー（修正差分と対応内容）とする。検証で新規の高指摘が出た場合は修正して同じペルソナで再検証する（フルセットへの復帰はしない）。前サイクルのペルソナ指摘が0件でも、修正差分が production コードに及ぶ場合は Step 4 をスキップせず、セキュリティエンジニアと QA エンジニアの2ペルソナで検証レビューを行う（スキップできるのは修正差分がテスト・設定・フォーマットのみの場合に限る）。詳細は `quality-check` SKILL.md Step 4 を正とする。

**サイクル内で即時に対応する工程（例外）**: 次の2つは指摘としてサイクル末尾に持ち越さず、その場で1回だけ修正してから次工程へ進む。

- **Lint 違反**: 決定的自動修正（`eslint --fix`、フォーマッタ等）を先に適用し、残った違反を AI が修正して静的チェックを再実行する（修正1パス + 確認1パス）。Lint はルールで矯正する層であり、修正が判断を要さないため持ち越す意味がない。確認パスで違反が残った場合、それ以上は Step 2 で繰り返さず、残存違反を**高指摘**としてそのサイクルの統合指摘に加える（この場合そのサイクルの Step 4 は実行しない — 上記「サイクルの構成」）。同一ルール × 同一ファイルの違反が確認パスで再発した場合（修正が振動している兆候）は `lint_abort_reason: "oscillation"` を記録し、ルール自体が不適切な可能性をユーザーに提示する。自動修正のみで完結したパス（AI の修正を伴わない実行）は `lint_cycles` にカウントしない。
- **ユニットテストの失敗**: 失敗の放置は後続工程（ペルソナレビューへの入力・統合指摘の判断）の前提を壊すため、その場で修正して再実行する。それでも失敗するテストは**高指摘**として統合指摘に加える（この場合そのサイクルの Step 4 は実行しない — 上記「サイクルの構成」）。

1サイクルの起点となる「`lint:all` 実行」は、`lint-scaffolding` 導入済みのプロダクトでは `lint:all` の実行を、未導入のプロダクトでは **CLAUDE.md に登録された静的チェックコマンドの実行**を指す。

**test-design 遡及実行の上限**: メモが欠落していた場合の遡及実行によるテスト補完は、1サイクルあたり最大5件（ファルシフィケーション項目を優先）とし、残りは統合指摘（中）として次サイクルに持ち越す。

**打ち切り時のゲート挙動**: サイクル上限・停滞で打ち切った場合、ユーザーの明示承認なしに `.quality-check-passed` を作成してはならない。承認を得た場合は、その事実と理由を `.quality-check-report.json`（`gate_override`）に記録する。

## 5.5. 開発プロセスのレビュー一本化

§5 が `quality-check` の内部（Lint 修正・ペルソナレビュー）の反復を**防護**するのに対し、本節は開発プロセス側の**レビュー地点を限定**する。実行実測（docs のみの変更に対しサブエージェント起動 約30回・推定240万トークン超。フェーズ2のマージゲート実測 — 当該 PR の quality-check レポート4サイクル分 — で、タスク単位レビューが捕捉した欠陥種はマージ前 quality-check の反証型ペルソナがすべて捕捉していた）が示すとおり、タスク単位のレビューループはコストに見合う独自の検出をほとんど生まない。

**原則**: 品質レビューはマージ前の `quality-check`（最終ゲート）に一本化し、**タスク実行時のレビューは行わない**。レビューループを持つのは「文書の作成時」と「マージ前」の2点のみとする。設計・計画のレビューは基本 1 周。

| ルール | 内容 |
|---|---|
| 開発中レビューの廃止 | 実装計画の実行中（サブエージェント実行・インライン実行を問わず）に、タスク単位のスペック照合レビュー・品質レビュー、および**計画実行末尾の whole-branch 最終レビュー**（subagent-driven-development が定めるもの — 修正ディスパッチ・再レビュー含む）を**行わない**。後者はマージ前 `quality-check` Step 4（全差分への多ペルソナレビュー）と対象範囲が同一であり、二重実行になる。実装者のセルフレビュー（テスト実行・自己確認）のみで次タスクへ進み、品質保証はマージ前の `quality-check` が一括して担う |
| 文書レビューの維持 | スペック文書（設計）と実装計画文書の作成時レビューループは維持する。**専任レビュアーによる基本 1 周。レビューが高指摘を出した場合、または文書が大規模な場合（実装計画: タスク数 8 超、または複数コンポーネント / 配布物にまたがる。設計文書: 変更対象が 3 ファイル群以上にまたがる、または既存の規範文書（policy / スキル / スキーマ）の改訂を伴う）に限り追加し、上限 3 周・超過時ユーザーエスカレーション。計画レビューの後にユーザー確認は求めない**（ユーザー確認は設計完了時点の 1 回）。この規定は本書が課すものであり、superpowers スキル側の「インラインで自己修正・再レビュー不要」の記述を上書きする（上限値・大規模判定の数値の単一ソースは本行。テンプレートは「基本1周」という規範のみ引用してよく、上限・大規模判定の数値は転記しない）。誤った設計・計画の上に実装を積む事故は最終ゲートでは防げないため、ここだけは前倒しの価値がある |
| モデル階層 | 設計・計画のレビュー（設計文書・実装計画に対するレビュー）は作成側と同じ最上位階層（Claude: `fable`、なければ `opus`。Codex: `gpt-5.6-sol` / `high`）。純粋なドキュメントのレビュー（README・`documents/` 等の記述内容の確認で設計判断を含まない）は `sonnet` / `gpt-5.4-mini` 可。実装サブエージェントは設計と計画がある前提で既定 `sonnet` / `gpt-5.6-terra`、計画で「判断を要する」と明記したタスクのみ `opus`（Codex: `gpt-5.6-sol` / `high`）。quality-check ペルソナは `opus` / `gpt-5.6-sol` `high`。Haiku は使わない。 |
| フェーズ予算 | 実装計画にサブエージェント起動数の目安を記載し、超過見込み時はユーザーにエスカレーション（従来の目安値はタスク単位レビュー込みの実測に基づくため、本節適用後の実測で再校正する） |
| 設計レビューの観点（例外分類） | 例外の握る / 伝播の分類を変える設計は、catch ごとに呼び出し元を全件トレースし、(a) 呼び出し元が catch / finally 内 (b) フレームワークのリスナー / コールバック契約で例外が致命的になる (c) スレッド / プロセスの最外殻 (d) 後始末 + 再送出 に該当すれば境界として扱う。境界宣言はメソッド本文の全段が契約を満たすことを確認する（try が本文の一部しか覆っていなければ契約は成立しない）。境界でない側の見本（DB 障害だけを握り他の実行時例外は上へ出す）と対比して線引きする（#122） |

**quality-check の最終ゲートとの境界**: 本節が廃止するのは**開発中のレビュー**だけである。`quality-check` Step 4 の最終ゲートには従来どおり「高/中の指摘は全て対応」が適用される。完了条件は `quality-check` SKILL.md の「完了条件」節を正とする（本書には転記しない）。最終ゲートで指摘が多発した場合もタスク単位レビューを復活させるのではなく、指摘の性質に応じて対処する（機械検出可能なものは Lint 層へ、設計起因のものはスペック・計画レビューの観点へ反映する）。§5 の「打ち切り時のゲート挙動」は本節によって免除されない。

**反映先**: 本節の規範は (a) CLAUDE.md / AGENTS.md テンプレートの Plan Execution Rules 節・.cursorrules テンプレートの Review Consolidation 節、および各テンプレートの Subagent Model Selection 節、(b) 本節、(c) `quality-check` SKILL.md の「対応できるものは全て対応」の適用範囲限定 — の3点で実行体に届く。superpowers スキル本体（subagent-driven-development のタスク単位2段レビューと whole-branch 最終レビュー、brainstorming / writing-plans の「再レビュー不要」記述）は外部プラグインのため編集せず、指示優先度で上書きする。
