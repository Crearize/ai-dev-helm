# AI Quality Policy

AI が主体で開発を行うプロジェクトのための品質ポリシー。AI Coding Policy（どう書くか）に対して、本ドキュメントは **AI Quality Policy（何をもって「品質を確認した」と言えるか）** を定義する。

前提となる問題認識は2つある。

1. **テストの Green は「正しさ」を保証しない。** テストが通ることは「書いたテストの範囲で期待どおりに動いた」ことしか意味しない。期待値そのものが誤っていれば、Green は誤りを追認するだけになる。
2. **実装と検証が同じ最適化ループの中にある。** 実装した AI 自身がテストを書くと、テストを通すことが目的化し（リワードハッキング）、実装の誤りをテストが一緒に間違えるという相関故障が起きる。

このポリシーは、リスクに応じたゲートの強度・テスト層の選び方・期待値の根拠（テストオラクル）・反復工程の打ち切り基準を定めることでこの2点に対処する。`quality-check` スキル（`skills/project/quality-check/SKILL.md`）は本ポリシーを参照して実行され、リスクレベル判定・ゲート適用・ループ防護の判断根拠を本ドキュメントに置く（本ドキュメントは方針の定義、スキル側は実行手順であり、数値・基準はスキルに複製せず本書を単一ソースとする）。

> 参考記事: [AIが書いたテストのGreenは何を保証しているのか](https://qiita.com/y0us91/items/2feffd2cc6c672717973)（Qiita, y0us91）

## 1. リスクレベル定義

変更差分から `quality-check` Step 1 でリスクレベルを判定し、`.quality-check-report.json` に `risk_level` として記録する。

| レベル | 判定基準（変更内容ベース） |
|---|---|
| High | 認証・認可、決済・課金、データ整合性に関わる書き込み処理、外部 API 連携、マイグレーション、セキュリティ設定 |
| Medium | 上記以外の業務ロジック（Service 層 / ドメインロジック / 状態遷移を持つ処理） |
| Low | UI 表示・文言・スタイル、ドキュメント、設定値の軽微な変更、純粋なリファクタ |

複数領域にまたがる場合は最も高いレベルを採用する。判定に迷う場合は1段階高いレベルに倒す。

## 2. リスクレベル別ゲートマトリクス

| ゲート | High | Medium | Low |
|---|---|---|---|
| 静的チェック（決定的チェック層） | 必須 | 必須 | 必須 |
| ユニットテスト | 必須 | 必須 | 必須 |
| test-design スキル（テストオラクル定義） | 必須 | 必須 | 不要 |
| ミューテーションテスト（差分スコープ） | 必須（スコア閾値 80%）※未導入時はスキップ記録 | 必須（閾値 70%）※同左 | 実行しない |
| ペルソナレビュー | 変更領域で決まる（quality-check Step 4 の段階化 / 縮退ルール） | 変更領域で決まる（同左） | 変更領域で決まる（同左） |
| E2E | 領域テーブルに従う（※適用例参照） | 領域テーブルに従う（同左） | 領域テーブルに従う（同左） |

閾値はプロダクト側のハーネス設定ファイル（下記「上書きの契約」）で上書き可能とする。

> **上書きの契約**: 上書きはプロダクト側のハーネス設定ファイル（`CLAUDE.md` / `AGENTS.md` / `.cursorrules` のうちプロダクトが使用するもの。複数を併用する場合は全ファイルに同じ値を記載する。値が食い違う場合は最も厳しい値を採用し、食い違いの事実をユーザーにエスカレーションして是正を求める）に次の記法で記載する。
>
> ```markdown
> ### Quality Gate Overrides
> <!-- quality-policy.md §2 の契約に従う。High リスクゲートを弱める設定は禁止 -->
> - mutation_threshold_high: 80
> - mutation_threshold_medium: 70
> - mutation_budget_minutes: 15
> ```
>
> 上書きキーは `mutation_threshold_high` / `mutation_threshold_medium` / `mutation_budget_minutes` の3つのみとする（上の例の値は本書の既定値そのもの）。ブロックを置かない場合、および記載のないキーは、本書の既定値が適用される。加えて、上書きには次の制約を課す。
>
> - High リスクのゲートを弱める上書きは**禁止（MUST NOT）**。
> - ゲートパラメータ（閾値・バジェット）を変更するハーネス設定ファイルの差分は「ハーネスのみ変更の免除」の対象外とし、必ず quality-check（最低でも縮退レビュー）を通す（hook の免除判定にも同カーブアウトが実装されており、ゲートパラメータ変更を含む差分はフラグなしでのマージがブロックされる）。
> - 既定値から乖離した上書きを適用した場合は、その事実と理由を `.quality-check-report.json` の `gate_parameter_overrides` に記録する（キー定義は `quality-check-report.schema.md` を参照）。
> - HTML コメント（`<!-- -->`）の内側、および markdown コードスパン・コードフェンス内に置かれた `### Quality Gate Overrides` ブロックとキー記載は**宣言とみなさない**（無効。既定値が適用される）。テンプレートはこの形（コメントアウト）で雛形を配布する。有効化はコメント解除によって行い、その編集自体がマージゲートの対象になる。quality-check 実行体も hook もこの解釈に従う。
> - キーの照合は**大文字小文字を区別せず、区切り文字（`_` / `-` / 空白）も区別しない**（`Mutation-Threshold-High` は `mutation_threshold_high` と同一の宣言とみなす）。正規表記は snake_case とし、それ以外の表記を見つけた場合は宣言として扱ったうえで、正規表記への是正をユーザーに求める。quality-check 実行体も hook もこの規則に従う。
> - **1つのファイル内に同一キーを複数回記載してはならない（MUST NOT）。** 複数記載があり値が食い違う場合、値は不定として扱う: quality-check 実行体はユーザーにエスカレーションして是正を求め、hook は宣言状態を判定不能（免除なし）として扱う。

**マトリクス優先順位原則（一方向）**: 本マトリクスは各ゲートの**強度**（閾値・要否の厳しさ）を定める。`quality-check` の変更領域別ステップ適用テーブルがステップを実行しないと定めている場合、リスクマトリクスの「必須」はそれを覆さない（逆方向の上書きはしない）。領域テーブルで `-` のステップはリスクレベルに関わらず実行しない。Step 3.5（ミューテーション）と test-design の照合は領域テーブルの Step 3 欄に従う（ユニットテストを実行しない領域ではいずれも実行せず、`out_of_scope` として記録する。記録キーは `.quality-check-report.json` の `test_design`）。**未実行理由の記録もこの優先順位に従う**: 領域による対象外（`out_of_scope`）と Low リスクによる非実行（`low_risk` / `not_required`）の双方に該当する場合は、領域による対象外を先に記録する。静的チェック（決定的チェック層）行が担保すべき内容はチェック基準カタログ（`static-check-standard.md`、配布後は `documents/development/static-check-standard.md`）に定義する。

なお、マトリクス自身がリスクベースで「不要」「実行しない」と定めている場合（Low の test-design・ミューテーション）はそのとおり実行しない。本原則は領域テーブルが実行しないと定めたステップをリスクレベルで復活させないためのものであり、その逆ではない。

（※）**適用例**: E2E は領域テーブルで E2E 欄が定義されている領域（backend / frontend / 複合）で実行する。infra / docs のみの変更は High リスクでも領域テーブルに従い E2E をスキップする。同様に、ペルソナレビューの段階化 / 縮退の選択も**リスクレベルではなく変更領域**で決まる（コード変更を含めば段階化、docs / infra のみなら縮退）。

**ミューテーションテストの「必須」についての注記**: 「必須」はミューテーションテストが導入済みのプロダクトでの話であり、通過不能条件ではない。プロダクトにミューテーションテスト設定（Stryker / PIT）が存在しない場合、`quality-check` Step 3.5 はブロックせずスキップし、`mutation: { executed: false, reason: "not_configured" }` を記録した上で、`lint-scaffolding` の実行を推奨するメッセージを出す。

**ミューテーションテストの実行ポリシー**: ミューテーションテストは**ローカルで実行し、CI には組み込まない**（実行時間がそのままコストになるため）。CI はビルド確認の位置づけを維持する。

**ペルソナレビュー行についての注記**: 適用ペルソナセットの具体的な条件（段階化時は差分規模に応じ3〜6ペルソナ、縮退時は領域別の縮退セット）は `quality-check` SKILL.md Step 4 を正とする（§5 参照）。

## 3. テスト層選択の原則（テストトロフィー）

**原則: テストの本数ではなく、Failure Mode に対して最も適切なテスト層を選ぶ。**

「テストトロフィー」とは、静的解析を土台に置き、その上のユニットテストと統合テストを厚く、頂点の E2E を最小限に保つテスト配分モデルである。本ハーネスでは土台の静的解析層を Step 2（決定的チェック層）が担う。

カバレッジ率やテスト件数は目的ではない。「この変更はどう壊れうるか（Failure Mode）」を先に列挙し、その壊れ方を最も確実に捉えられる層でテストする。

| Failure Mode | 推奨テスト層 | 例 |
|---|---|---|
| 入力境界（ゼロ・負値・null・オーバーフロー・精度） | ユニット | 金額計算の境界値 |
| 状態遷移・不変条件 | ユニット + 統合 | 注文ステータスの遷移制約 |
| 並行・リトライ・冪等性 | 統合（DB/キュー状態の観測込み） | 二重配信防止 |
| 外部依存（API・時刻・乱数） | 統合（契約テスト・スタブ境界） | 外部 API 失敗時の挙動 |
| 権限・認可 | 統合 + E2E | 他ユーザーのリソースへのアクセス拒否 |

**統合テストの実行位置**: 統合テストは Step 3 のテストコマンドに含めて実行する（テストコマンドの定義はプロダクトの CLAUDE.md）。上表で「統合」を推奨層としたケースに独立したゲートは設けない。

**カバレッジ目標との関係**: カバレッジ目標（`development-policy.md` §9）は**下限**として維持する。本節が否定するのは、カバレッジ率の達成をテスト十分性の**証明**として扱うことである。なおミューテーションスコアはカバレッジ率とは別の指標である（80% という数値が両方に登場するが無関係 — カバレッジは「実行された行の割合」、ミューテーションスコアは「意図的な変異をテストが検出できた割合」を測る）。

## 4. テストオラクル原則

**テストオラクル（Test Oracle）**: テストの実行結果が正しいかどうかを判断する基準・情報源（仕様書、要件、計算根拠など）。DB 製品の Oracle とは無関係。本ドキュメントでは「テストオラクル（期待値の根拠）」と表記する。

原則は次のとおり。

- **期待値の根拠は実装より先に定義する。** 各テストの期待値がどこから来たのか（仕様書・要件・計算根拠）を、実装コードを書く前に明示する。
- **実装の出力をそのまま期待値にすることを禁止する。** 実装を動かして得られた値をコピーして期待値に据える行為は、実装の誤りをテストが追認する構造そのものであり、検証として無効である（スナップショットの無検証な更新も同じ）。
- テストコードを書けることと、正しいテストオラクルを設計できることは別能力である。前者ができるからといって後者が担保されるわけではない。

High / Medium リスクの変更では、実装**前**に `test-design` スキルを実行してテスト設計メモを作成する。メモには最重要リスク・保証すべき状態遷移と不変条件・Failure Mode からテスト層へのマッピング・テストオラクル定義・ファルシフィケーション項目（「この実装が間違っていることを証明する」ための入力・シナリオ候補）を含める。`quality-check` Step 3 はこのメモとテストを照合し、メモが存在しない場合はエラーにせずその場で `test-design` を遡及実行して不足テストを補完してから先に進む。

## 5. 反復工程のループ防護

ペルソナレビューで過去に発生した「指摘 → 修正 → 再指摘」の無限ループと同じ問題は、Lint 修正・ミューテーションのテスト追加でも起こりうる。

**原則**: 反復を伴う全工程は「①サイクル上限 ②停滞・振動検出 ③縮退 ④ユーザーエスカレーション」の4点セットを持つ。実行時間バジェットはミューテーションのみに定義する（Lint・ペルソナレビューにはバジェットを設けない — サイクル上限で足りる）。

| 工程 | サイクル上限 | 停滞・振動検出 | 上限到達・停滞時の挙動 |
|---|---|---|---|
| Step 2: Lint 違反修正 | 3サイクル（1サイクル = `lint:all` 実行 → 修正） | 同一ルール × 同一ファイルの違反が2サイクル連続で再発（修正が振動している兆候） | ユーザーに判断を仰ぐ（ルール自体が不適切な可能性も提示する） |
| Step 3-2: test-design の遡及実行によるテスト補完 | 1回の quality-check あたり最大5件（ファルシフィケーション項目を優先して補完する） | 再照合しても不足件数が減らない | 部分結果を `test_design.gaps_addressed` に記録してユーザーに判断を仰ぐ |
| Step 3.5: ミューテーションのテスト追加 | 5ループ | 2ループ連続でスコア改善なし → 上限を待たず早期打ち切り | 部分結果とスコアを記録してユーザーに判断を仰ぐ（閾値未達のまま通すか、テスト戦略を見直すか） |
| Step 4: ペルソナレビュー | 既存ルール維持（10サイクル上限・高/中指摘時のみ次サイクル・指摘元ペルソナのみ再確認） | 既存ルール | 既存ルール |

ペルソナレビューのルールは `quality-check` SKILL.md の **Step 4 全体**（ペルソナ段階化ルール・レビュー縮退ルール・4-3 サイクルルールを含む）を正とし、本ドキュメントからは参照のみとする（二重管理を避けるため、詳細の追記・改変は SKILL.md 側で行う）。ペルソナセットの選択が変更領域で決まる点は §2 のペルソナレビュー行注記を参照。

**Lint 修正の縮退**: AI による修正の前に必ず決定的自動修正（`eslint --fix`、フォーマッタ等）を適用し、AI が触る違反そのものを減らす。自動修正のみで完結したパス（AI の修正を伴わない実行）は3サイクルの上限にカウントしない。

1サイクルの起点となる「`lint:all` 実行」は、フェーズ3で `lint:all` が整備されるまでは **CLAUDE.md に登録された静的チェックコマンドの実行**と読み替える（`lint:all` はフェーズ3以降の呼称）。

Lint の3サイクル上限は **Step 2 自身のループにのみ適用される**。Step 4 のレビューサイクル中に修正差分の影響範囲を再検証するために静的チェックを再実行する場合、それは Step 2 のサイクルとしてカウントしない（レビューサイクル側の上限で管理する）。

**ミューテーションのループ手順と縮退**: 1ループは「生存ミュータントの分析 → 不足しているテストの追加 → 再実行」で構成する。等価ミュータント（動作が変わらない変異）は理由を記録して対象から除外できる。4点セットの③縮退にあたるのは**スコープの絞り込み**であり、対象ファイルをリスクレベルの高いものから優先して絞る（下記バジェット参照）。

**ミューテーションの実行時間バジェット**: 1回の quality-check あたり既定15分（ハーネス設定ファイル（§2「上書きの契約」）で上書き可）。実行前にドライラン結果からバジェット超過が見込まれる場合は、リスクレベルの高いファイル優先で対象を絞り、絞った事実を `mutation.scope_reduced` として記録する。バジェット超過時は途中結果で打ち切り、ユーザーに判断を仰ぐ。ミュータント単位のタイムアウトは Stryker / PIT の組み込み機構をそのまま使う。

> バジェットの上書きも §2「上書きの契約」に従い、ハーネス設定ファイルの `Quality Gate Overrides` ブロックに `mutation_budget_minutes` として記載する。記載がない場合は本書の既定値（15分）が適用される。

**打ち切り時のゲート挙動**: 打ち切り・閾値未達で終了した工程がある場合、ユーザーの明示承認なしに `.quality-check-passed` を作成してはならない。承認を得た場合は、その事実と理由を `.quality-check-report.json` に記録する。

## 5.5. 開発プロセスのループ防護（レビューの一本化）

§5 が `quality-check` の内部（Lint 修正・ミューテーション・ペルソナレビュー）の反復を対象とするのに対し、本節は**開発プロセス側 — 実装計画をタスク単位で実行する際のレビューの置き場所**を対象とする。実行実測（docs のみの変更に対しサブエージェント起動 約30回・推定240万トークン超。タスク単位レビューが捕捉した欠陥種は、マージ前 quality-check の反証型ペルソナがすべて捕捉していた）が示すとおり、タスク単位のレビューループはコストに見合う独自の検出をほとんど生まない。

**原則**: 品質レビューはマージ前の `quality-check`（最終ゲート）に一本化し、**タスク実行時のレビューは行わない**。レビューループを持つのは「文書の作成時」と「マージ前」の2点のみとする。

| ルール | 内容 |
|---|---|
| タスク単位レビューの廃止 | 実装計画のタスク実行時（サブエージェント実行・インライン実行を問わず）に、そのタスクに対するスペック照合レビュー・品質レビューを**行わない**。実装者のセルフレビュー（テスト実行・自己確認）のみで次タスクへ進む。品質保証はマージ前の `quality-check` が一括して担う |
| 文書レビューの維持 | スペック文書（設計）と実装計画文書の作成時レビューループは維持する（各最大3周 — superpowers スキルの既定。超過時はユーザーへエスカレーション）。誤った設計・計画の上に実装を積む事故は最終ゲートでは防げないため、ここだけは前倒しの価値がある |
| モデル階層 | 文書レビュー（スペック・計画）は sonnet 可。opus は quality-check ペルソナに限定する。**本行は「レビュー系サブエージェント」の階層のみを対象とし、実装サブエージェントの階層（テンプレートの Subagent Model Selection 表）は変更しない** |
| フェーズ予算 | 実装計画にサブエージェント起動数の目安を記載し、超過見込み時はユーザーにエスカレーション |

**quality-check の最終ゲートとの境界**: 本節が廃止するのは**タスク単位の開発中レビュー**だけである。`quality-check` Step 4 の最終ゲートには従来どおり「高/中の指摘は全て対応」が適用され、完了条件（必須修正 = Priority: High が0件）も変わらない。最終ゲートで指摘が多発した場合もタスク単位レビューを復活させるのではなく、指摘の性質に応じて対処する（機械検出可能なものは Lint 層へ、設計起因のものはスペック・計画レビューの観点へ反映する）。§5 の「打ち切り時のゲート挙動」は本節によって免除されない。

**反映先**: 本節の規範は (a) CLAUDE.md / AGENTS.md / .cursorrules テンプレートの Plan Execution Rules・Subagent Model Selection 節、(b) 本節、(c) `quality-check` SKILL.md の「対応できるものは全て対応」の適用範囲限定 — の3点で実行体に届く。superpowers スキル本体（subagent-driven-development のタスク単位2段レビュー等）は外部プラグインのため編集せず、指示優先度で上書きする。

## 6. 記録

全工程のループ回数・打ち切り事由を `.quality-check-report.json` に記録する（`lint_cycles` / `mutation.loops` / `mutation.aborted_reason` / `mutation.scope_reduced` 等）。リスクレベル（`risk_level`）、ミューテーション結果（`mutation`）、テスト設計メモの照合結果（`test_design`）も同ファイルに記録する。打ち切り工程をユーザー承認のもとで通した場合は、その承認の事実と理由も記録する（§5「打ち切り時のゲート挙動」）。

フィールドの完全な定義は `skills/project/_schemas/quality-check-report.schema.md` を参照する。

> **配布時の注記**: プロジェクトスキルを導入していない（superpowers スキルのみ導入した）プロジェクトでは、本書が参照する `quality-check` スキルとレポートスキーマのファイルが存在しない。これらの参照は該当ファイルを導入した時点で有効になる。
