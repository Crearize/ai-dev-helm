# Finishing a Development Branch

Confirm the final change has completed the project's independent quality-check and required checks. Evidence must describe the current tree: rerun affected verification after material edits or integration changes, and report unresolved failures. Do not add another whole-branch review or repeat an unchanged successful test suite merely to follow this skill.

Determine the repository, branch, base, worktree ownership, and uncommitted changes with read-only Git commands. Verify the intended target from the plan, upstream, or conversation before integrating.

Follow the integration action already authorized by the user. The design approval already covers commits, feature-branch pushes, creating the PR and the merge. First, if the project's rules require the user's approval for the merge, or the merge automatically releases, publishes or deploys to production - an environment that customers or users rely on (exception X2; an automatic deploy to an environment for checking behavior (such as staging) that does not touch production - the production database, live payments, or sending to real customers and the like - is not X2; judge by the effect on customers or users, not by the name) - finish the reviewable result and put that question in the final message. Only an answer to that item, or an instruction that names the operation and its target (range), counts as an X2 OK - not the design approval, a generic "continue", or an instruction that names no range. Otherwise look at the deviations from the design - both the spec / plan record and the PR body's deviation section. If there are none, merge with the project's merge procedure once quality-check is complete. If there are any, they change what was approved: finish everything else but create the quality-check flag only after the user's confirmation, ask in the final message as a separate decision ("merge with these deviations?"), and merge after the user's confirmation. A deviation that appears after that confirmation needs a new confirmation. Do not present an approval menu again. End with the final message of `documents/development/development-policy.md` §1.0 "承認後の進め方".

For a project that promotes main to a production branch (`release` or similar), the X2 question covers everything that goes out (§1.0 "承認後の進め方" 8). Before asking, run `git fetch origin` and fix the end SHA of the source. List the PRs not yet promoted up to that SHA: with merge-commit promotion, `git log --first-parent --oneline origin/<release>..<SHA>`; with squash promotion, main's commits never become ancestors of the production branch, so start from the previous source (the SHA recorded in the last promotion PR, or the first-parent main commit whose tree equals `origin/<release>^{tree}`); if no starting point is found, do not guess a list - write that it was not found in the final message. Show the list and the short SHA in the final message. As for any X2 OK, only an answer to the item that shows the list and the SHA, or an instruction that names the operation and the range, counts (on a "promote it" that names no range, build the list and the SHA and ask). Promote exactly that SHA; anything that lands before or after the OK stays out. When the promotion goes through a PR, do not use main as its head (push a temporary branch at the SHA and use it, for example `git push origin <SHA>:refs/heads/promote/<short SHA>`), or merge with `gh pr merge --match-head-commit <SHA>`. With squash promotion, write the source SHA in the promotion PR body (the next starting point). When this PR is not merged yet, add "this PR (after merge)" to the list; after the merge, if the first-parent range `<the SHA you asked with>..<this PR's merge commit>` holds only this PR, use that merge commit as the end, otherwise rebuild the list and ask again. After the OK, the AI merges and promotes; do not hand those operations back. The commands depend on the merge method: the project's own procedure holds the exact steps.

A project with no remote integrates into main without a PR. "No remote" means the trunk has no remote-tracking ref (such as `origin/main`), which includes a project whose only remote is push-only; do not push the feature branch to such a remote. With main open in another worktree: (1) finish quality-check in the feature worktree so the flag matches HEAD; (2) before touching the main checkout, run four checks: (a) no tracked file has an uncommitted change (`git -C <main checkout> status --porcelain --untracked-files=no` prints nothing); (b) no untracked file of the main checkout, ignored ones included, sits at a path the feature adds (see the next paragraph); (c) in the feature worktree, `git merge-base --is-ancestor main HEAD` succeeds - if it fails, do not detach: merge main into the feature, re-run quality-check, then integrate; (d) `git push . HEAD:main` is usable in this project (no deny rule in the agent settings such as `Bash(git push:*)`, no project rule against it). If (a) or (b) fails, do not detach; stop integrating, leave the user's work in progress untouched and report in the final message only the number of hits and the feature-side paths (exception X3). (3) If push is usable, in the checkout that has main open, run `git switch --detach`; in the feature worktree, run `git push . HEAD:main` (git refuses anything but a fast-forward); in the main checkout, run `git switch main`, discarding its output (see below). (4) If it is not, or a deny rule refuses the push after the detach, keep main detached and use the local merge of the `branch-workflow` skill, run where the flag is (the gate reads the flag of the checkout that runs the command, and the main checkout has none): in the main checkout, `git switch --detach` (unless it already is); in the feature worktree, `git switch main`, `git merge --no-ff <feature>`, `git switch <feature>`; in the main checkout, `git switch main`, discarding its output. (5) Delete `.quality-check-passed`.

Check (b) without exposing names. Never list the main checkout's untracked files: their names (the user's work in progress, customer data) must not reach the conversation, and other untracked files do not block the integration, so leave them alone. Name only the feature's paths and count: in the feature worktree, list them with `git -c core.quotePath=false diff --name-only --no-renames --diff-filter=A main...HEAD` (renamed targets and non-ASCII names come out as they are); if the list is empty, skip the check (`git ls-files --others` without a path lists every untracked file); otherwise, for each path, count `git -C <main checkout> ls-files --others -- ":(literal,icase)<path>" | wc -l` (PowerShell: `| Measure-Object`). `literal` keeps characters such as `[id]` from acting as a glob, `icase` catches case-only differences (Windows, macOS), and there is no `--exclude-standard`, so ignored files of the user are protected too; a path that is a directory on the main side counts its files. `ls-files` has no `--pathspec-from-file`: pass the paths as arguments.

If the checks passed but the final `git switch main` fails (a collision the checks cannot see, such as a parent of a path the feature adds being a file on the main side), its output names the main-side files - run it as `git -C <main checkout> switch main >/dev/null 2>&1` and read only the exit code. Do not touch the user's files: leave the main checkout detached at the commit before the integration (the only case it stays detached) and report in the final message that it failed and the feature-side paths (exception X3). If the push or the merge is refused for a reason other than a deny rule (the quality gate, git's non-fast-forward refusal and the like), put both checkouts back (`git switch <feature>` in the feature worktree if it is on main, `git switch main` in the main checkout) and re-run quality-check (after merging main into the feature if main has moved on); otherwise never leave the main checkout detached. Use this only when the trunk has no remote-tracking ref. With the feature and main in one checkout, finish quality-check on the feature, switch to main and run `git merge <feature>`: the quality gate checks that the flag names that branch's tip and that main has nothing the branch lacks. Delete `.quality-check-passed` after any merge into main.

Keep the project's branch protections and quality gate. A local merge or main push is not a substitute for a required PR. Investigate rejected pushes; do not force-push or bypass a gate without explicit applicable authorization.

When creating a PR, describe the problem, resulting behavior, and observed checks. Preserve the worktree for feedback. On an environment-owned worktree, use supported platform operations and leave cleanup to its owner.

Clean up only a worktree you created and only after its work is safely integrated or explicitly discarded. Check for uncommitted and ignored files before removal. Never force removal of files that exist nowhere else; resolve their disposition with the user. Do not infer permission to discard work from an integration request.
